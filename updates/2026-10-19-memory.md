# 2026-10-19 — Correct memory without reviving stale facts

**For:** developers deciding what stored information belongs in a model's next request.

The [memory lifecycle lab](../labs/memory-lifecycle/README.md) executes a SQLite write/retrieve/correct/expire/retract sequence. It retains source IDs and revision history, rejects stale writers, demonstrates namespace selection, and builds a concrete context packet. Reopening the database preserves the correction.

The important failure boundary is expiry: the application selects the latest observed revision before testing validity. An expired correction returns an unavailable status rather than exposing the older, superseded value. This is actual application execution, not a generated model response.

**Evidence:** a recorded transcript, fresh-database replay matching every event, and ten passing tests. The storage module measured 95% statement coverage with Coverage 7.16.2. Source truth, authentication, direct database access, and privacy deletion are not implemented or inferred from those tests.

**Action:** carry provenance and validity with stored facts; specify how corrections and retractions affect retrieval. The context chapter, roadmap, developer lab path, and coverage audit now link the example. No model account or third-party dependencies are required.
